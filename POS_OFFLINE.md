# Локальная касса: архитектура и границы

## Что работает

В Electron поиск в загруженном каталоге, сканирование, изменение количества,
скидки, ручная цена, отмена и откладывание корзины выполняются на устройстве.
Ответ UI выдаётся после записи SQLite, без ожидания HTTP. При возврате сети
корзины синхронизируются в фоне; перезапуск не очищает очередь.
Это локальная работа с черновиками, **не автономная фискализация продажи**.

Первый запуск кассовой сессии, загрузка каталога, завершение продажи, возврат,
закрытие смены и серверная история требуют сети. Существующие облачные адаптеры
WebKassa/ReKassa не предоставляют этому приложению локальный интерфейс ККМ.
Для полноценной продажи без интернета нужен документированный локальный SDK/API
конкретной ККМ, отдельный платёжный адаптер и испытания на реальном оборудовании.
Приложение не объявляет оплату успешной без подтверждённого фискального чека.

## Слои

### Сканер на рабочем экране

На основном экране продаж USB/Bluetooth-сканер в режиме клавиатуры не требует
фокуса в поиске. Автоматический фокус ставится на рабочую область, а не input;
ручное нажатие на поиск открывает клавиатуру как прежде. Диалоги, другие экраны,
input/textarea/contenteditable не перехватываются. Терминатор сканера не нажимает
случайно сфокусированную кнопку оплаты/отмены.

Поддерживаются Enter/Tab, ведущие нули и GS1-разделитель (в том числе Ctrl+]).
Без фокуса распознаётся быстрый пакет из 4–512 символов: интервал до 80 мс,
средний до 40 мс. Незавершённые пакеты не отправляются автоматически; прерванные
и слишком длинные отбрасываются целиком. Для сканеров с искусственной задержкой,
коротких внутренних кодов или без завершающего Enter/Tab остаётся ввод в поле;
настройку устройства следует проверить на реальном оборудовании.

Распознавание пакета находится в `barcode-scanner-buffer.ts`, DOM-адаптер —
в `use-checkout-barcode-scanner.ts`. Найденный код передаётся существующей команде
сканирования без дублирования бизнес-логики продаж.

### Компоненты приложения

- `src/shared/pos`: команды, строгие схемы IPC, чистый reducer корзины, Decimal-расчёты, GS1.
- `src/main/pos/pos-database.ts`: SQLite WAL/FULL, шифрование, индексы каталога, долговечная очередь.
- `src/main/pos/pos-service.ts`: авторизация, локальные операции, синхронизация и восстановление оплаты.
- `src/main/pos/pos-catalog.ts`: cache-aside поиск, постраничная фоновая загрузка, ограничение запросов и повторы с паузами.
- `src/main/pos/pos-worker.ts`: отдельный поток для диска и поиска.
- `src/main/pos/pos-ipc.ts` и preload: ограниченный мост из доверенного главного окна.
- `src/renderer/src/common/lib/local-pos.ts`: клиент моста; React-компоненты отображают состояние и отправляют команды.

В обычном браузере остаётся существующий HTTP-путь. Офлайн-поведение реализовано
для desktop-приложения, не для PWA. Типы HTTP-ответов пока переиспользуются из
`renderer/common/api/responses`; это type-only зависимости без React/runtime-кода.

## Данные и синхронизация

Одна локальная запись содержит корзину, локальную ревизию, подтверждённую серверную
версию, неизменяемую отправляемую команду и состояние оплаты. Скан известного локально товара не ждёт сеть.
Пока отправляется старый снимок, новые изменения сохраняются независимо от него.
Потерянный ответ приводит к повтору того же `command_id` и payload, а не новой операции.
Backend повторно проверяет сессию, права, товары, цены, налоги и версию; суммы клиента
не считаются доверенными. Завершённые и фискализируемые чеки не перезаписываются.

Конфликт нельзя автоматически разрешить правилом «последний победил».
Кассир сравнивает версии; перед выбором сохраняется зашифрованная локальная копия.
Новые цены/налоги требуют повторного подтверждения оплаты. Причина отмены и
антифрод-событие сохраняются в очереди; наличие видеозаписи за период отсутствия
сети эта реализация не гарантирует.

**97 тысяч товаров не загружаются каждые пять минут.** Один начальный обход
через `/v1/pos/catalog/page` по 250 товаров, без общего массива, COUNT и растущего
OFFSET. До первой страницы POS получает `/sync-start`, сохраняет исходный курсор
журнала и после обхода догоняет изменения через `/changes`. Правки и удаления
позади UUID-курсора поэтому не теряются. На кассе один фоновый запрос с паузами
250–499 мс. Частичный обход продолжается после перезапуска.

После начальной загрузки запрашиваются только изменения: обычный интервал при
активном POS около 15–30 секунд (таймер 15 секунд + cooldown/jitter). Без изменений
backend читает только индекс журнала, без выборки товаров. При большом импорте —
не более 20 порций по 250 на один запуск фоновой обработки, затем продолжение.
Ошибки: 30 секунд–5 минут плюс jitter, с учётом более длинного Retry-After;
ручная проверка не обходит паузу и не начинает новый полный обход.

Полный обход нужен повторно только без сохранённого курсора, после сброса поколения
или истечения доступного журнала (хранение минимум 7 дней с порционной очисткой).
Первый запуск этой версии поверх старого кэша также устанавливает безопасную
базовую точку через один обход; кэш и чеки не удаляются. Категории после начальной
загрузки перечитываются по изменениям журнала, не каждые пять минут.

SQLite обновляется порциями по 25, с передачей управления между транзакциями.
Товары доступны сразу после записи своей порции, даже если весь каталог ещё не загружен.
Неизменившиеся товары не перешифровываются и не переиндексируются; им обновляется
только отметка начального обхода. Дельты авторитетны независимо от `updated_at`
(изменение налогового fallback/НКТ может не увеличивать дату товара).
Удаления из журнала удаляют и товар, и FTS-индекс. Курсор подтверждается только
после сохранения всей порции; частично применённая порция безопасно повторяется.
Запоздавший адресный ответ не воскрешает уже удалённый товар. Это постепенно
согласующийся кэш, не глобальный мгновенный снимок всех касс.

Очередь чеков хранит отдельно ошибки синхронизации черновика, переноса оплаты на
проверку и события отмены. Сеть/408/425/429/5xx повторяются тем же `command_id` и
payload через 5 секунд–5 минут с jitter, учитывая Retry-After. Пауза сохраняется
в SQLite и не обходится повторным сканированием, кнопкой или перезапуском.
При недоступности сервера одна ошибка приостанавливает транспортную отправку,
а не вызывает запрос для каждого чека подряд. Локальная работа продолжается.
Окончательный отказ валидации сохраняется в конкретном чеке и не повторяется
по таймеру; остальные независимые чеки обрабатываются. Исправление корзины или
«Повторить отправку чека» разрешает новую попытку. Конфликт требует сравнения,
отказ доступа — подтверждения входа, неопределённая оплата — сверки с ККМ.

Поиск сначала читает SQLite. Если есть результат, HTTP не ждём. Если результата нет,
штрихкод/ID ищется через `/lookup`, текст — через `/search`; полученные товары
валидируются по организации и магазину и сохраняются локально. Текстовый промах
имеет debounce 200 мс, не более одного текстового HTTP-запроса; одинаковые адресные
поиски объединяются, одновременно их максимум 4. Не найденные коды кэшируются на
10 секунд, ошибки перегрузки ограничивают повторы. Адресный поиск не ждёт фоновую загрузку.
При отсутствии сети и локального товара именно этот товар получить нельзя;
остальные локальные операции доступны. Поздний ответ после смены чека не добавляет
товар в другую корзину. Права, сохранность чека и подтверждение оплаты не обходятся.
Остатки в локальный каталог не входят; окончательные проверки выполняет backend.

### Индикаторы синхронизации

Общая строка состояния находится над рабочей областью на всех экранах активной
локальной кассы: продажи, история, возвраты и другие разделы. Она также видна
в окне выбора товаров по категориям. В продажах есть подробности и действия
повторной проверки; рядом с полем сканирования — отдельный индикатор адресного поиска.

- Каталог: начальная загрузка или проверка изменений; число обработанных товаров
  или изменений за текущую обработку. Это не размер всего каталога и не процент.
- При паузе каталога показана ошибка и время, раньше которого автоповтор не начнётся;
  при успехе — время последней завершённой синхронизации (в подробностях/подсказке).
  Если есть остаток порций, показано «догоняем изменения»; если безопасному курсору
  мешают незавершённые транзакции PostgreSQL — «ожидаем транзакции сервера».
  Эти состояния не выдаются за полную синхронизацию и не мешают локальной работе.
- Чеки: фактическая отправка, количество чеков в очереди, ожидание связи или доступа.
  Пустая очередь отправки не означает подтверждение фискальной оплаты: очередь
  проверки оплаты и расхождения показаны отдельно.
  Раскрываемый список отправки показывает первые 50 чеков: ID, этап, код/описание
  ошибки и время следующей попытки. Общий счётчик включает всю очередь.
- Поиск: количество реально выполняющихся запросов отсутствующих товаров
  (штрихкод/ID и текст). Совпадающие запросы учитываются один раз. Чтение готового
  товара из SQLite не включает индикатор сетевой загрузки.

Индикаторы не блокируют интерфейс и не запускают загрузку каталога. Один общий
наблюдатель читает статус через IPC, объединяет события за 40 мс и дополнительно
проверяет локальное состояние раз в 15 секунд. Изменение индикатора поиска само
по себе не инвалидирует каталог и не порождает новый поиск. Если статус получить
не удалось, вместо устаревшего успеха показана причина ошибки.

Наблюдатель подписан на подключение/восстановление локальной смены и начинает
проверку после получения её профиля. Кэш статуса разделён по сменам. Ответ без
`sessionId` означает несовместимый старый локальный процесс; пустая/другая смена
и некорректный ответ показаны отдельными предупреждениями, а не бесконечной загрузкой.
Ожидание статуса ограничено 5 секундами в renderer и IPC, включая запуск worker.
При старом IPC без таймаута renderer сохраняет не более одного зависшего запроса;
поздний ответ не подменяет свежий статус. Кнопка «Повторить проверку статуса»
только читает статус: не переподключает кассу, не запускает синхронизацию и не
повторяет платежи. Этот таймаут не применяется к изменению/оплате чеков.

Для этих индикаторов не требуются отдельные миграции или скрипты; после обновления
нужно полностью перезапустить POS (`npm run dev` в разработке), чтобы обновился worker.

## Безопасность

- Профиль офлайн-доступа связан с точным токеном, пользователем, магазином и кассовой сессией.
  Максимум 8 часов после онлайн-проверки. Возраст смены кассы не сокращает срок
  доступа: иначе после 24 часов нельзя было даже войти и закрыть смену.
  Возраст 24 часа отображается предупреждением, без локального или серверного
  запрета по возрасту. Фактический отказ ККМ остаётся отказом, не успешной продажей.
  Это ограниченный локальный допуск, не продление JWT на сервере.
- При наличии сети доступ перепроверяется; отзыв прав блокирует дальнейшие операции.
  Ответ 401 не отзывает действующий локальный допуск: renderer обновляет JWT
  через общий single-flight refresh и заново проверяет кассовую сессию. 403 или
  подтверждённое завершение сессии не обходятся. Допуск не продлевается без проверки.
  Без сети отзыв нельзя узнать немедленно. Перевод часов назад ограничивается сохранённой отметкой времени.
- AES-256-GCM защищает записи и содержимое каталога; ключ защищён OS safeStorage.
  Имена/штрихкоды поисковых индексов, UUID и метаданные таблиц не зашифрованы.
  Это не защита от администратора с полным доступом к ОС; нужен шифрованный диск и защищённая учётная запись.
- Без защищённого хранилища ОС касса не переключается на незашифрованный режим.
  Нельзя удалять `userData/pos`, `device-key`, SQLite или WAL для исправления ошибки.
- IPC проверяет окно, главный frame, origin и строгую схему. Renderer не получает SQL,
  файловые пути, ключ шифрования или фискальные credentials.
- Неподтверждённая оплата сохраняется до HTTP-запроса и блокирует повтор/редактирование.
  Только этот чек остаётся неизменным. «Новый чек» переносит его в долговечную
  очередь проверки без отмены/новой фискализации и освобождает рабочую корзину.
  «Проверить оплату» восстанавливает результат; после доказанного отказа доступно
  «Вернуться к чеку». При этом новая корзина никогда не перезаписывается.
  Выйти или закрыть сессию с несинхронизированными операциями нельзя.

## Выкладка

После успешной отмены или подтверждённого возврата POS отправляет отдельный фоновый
anti-fraud-запрос. Если активной камеры кассы/магазина нет, backend возвращает нормальный
пропуск и не создаёт запись. Если камера настроена — создаёт задание захвата видео.
Синхронизация чеков и завершение операций не ждут этого запроса или видеозаписи.
Отправка ограничена 5 секундами и четырьмя одновременными запросами, без очереди повторов
и без автоматического изменения авторизации кассира. Сбой камеры/сети не откатывает
отмену/возврат; при офлайн-работе или перегрузке видеособытие может быть пропущено.
Поздняя синхронизация чека не запускает съёмку задним числом. Новых миграций anti-fraud нет.
Старые `cancellationEvent`/ошибки этапа `cancellation` могут оставаться в зашифрованной
локальной истории, но больше не отправляются, не входят в очередь и не препятствуют
выходу/закрытию смены. Несинхронизированные изменения самого чека и неопределённые
оплаты по-прежнему требуют синхронизации/проверки.

1. Резервная копия backend-БД; проверить новую версию на staging.
2. PostgreSQL 13+; применить прежние миграции и `1788912000000-index-pos-catalog-search`, `1788998400000-index-pos-catalog-nkt`, `1788998400001-create-pos-catalog-journal` через `npm run migration:run`. Режим `each`; два индекса создаются `CONCURRENTLY`, журнал/триггеры — транзакционно с lock_timeout 3 секунды. При занятой таблице миграция завершается ошибкой, её нужно повторить в тихое окно. Построение индексов планировать вне пика, контролировать CPU/IO.
   Также обязательна `1789084800000-normalize-pos-catalog-scope`: UUID-поля организации/магазина вместо `audience`. Подготовить сборку backend до запуска миграций. Порционный перенос истории сохраняет курсоры, повторная загрузка каталога из-за этой миграции не нужна. После финального переключения схемы сразу заменить старые backend-реплики: их SQL обращается к удалённому `audience`. Миграция возобновляется после сбоя; checkpoint удалять нельзя. Подробности — `maria-core-api/docs/pos-sync.md`.
3. Развернуть backend с `/v1/pos/catalog/sync-start`, `/page`, `/changes`, `/lookup`, `/search` и прежними API чеков. Затем обновить все POS: старые версии с `/page` продолжают периодические полные обходы и преимуществ дельта-синхронизации не получают.
4. Установить новый POS сначала на одну тестовую кассу. Подтвердить смену онлайн. Можно работать до окончания загрузки; для гарантированного поиска без сети дождаться полного каталога.
5. Проверить сканер, Data Matrix, принтер и WebKassa/ReKassa на тестовой ККМ.

Не откатывать миграции и не удалять журналы после начала реальной работы:
это уничтожает доказательства отправки, необходимые для безопасного повтора.
При откате клиента сначала выгрузить очередь; старый клиент не знает о локальных черновиках.

Каталог обновляется автоматически; отдельные seed/reindex-скрипты перед каждой
сменой не нужны. Статус показывает фоновую загрузку и число обработанных товаров.
Экран кассы запускает локальную сессию даже при наличии сессии в React Query cache.

После явного отказа WebKassa сервер разрешает отмену. Таймаут, дубликат или неизвестный
результат сохраняют блокировку; «Проверить оплату» ищет подтверждённый чек и завершает
его без повторной фискализации. Старый SENT без контекста требует отдельной сверки,
ID проблемного чека показывается после проверки. Фискальный конфликт нельзя решать
перезаписью через диалог обычных конфликтов корзины.

## Проверки

Автоматически: `npm test`, `npm run build`, `npm run lint`.
После сборки: `node scripts/smoke-pos-worker.mjs`; для Electron запускать тот же
скрипт с `ELECTRON_RUN_AS_NODE=1` через установленный executable Electron.

Проверка настоящего Electron и входа в уже активную смену:
`POS_SMOKE_AUTH_DELAY_MS=6000 POS_SMOKE_SHIFT_HOURS=25 node_modules/.bin/electron scripts/smoke-pos-network.cjs`.
Использует временный профиль и локальный тестовый HTTP-сервер, не рабочую БД.
Проверяет, что медленная проверка доступа и смена кассы старше суток не блокируют вход.

При ошибке доступа во время разработки полностью перезапустить `npm run dev`:
HMR интерфейса не обновляет уже запущенный POS worker. Проверка первоначального
доступа ждёт до 15 секунд, как интерфейс; истёкший access token обновляется через
общий механизм refresh без повтора бизнес-операций. Ошибки сети, формата ответа,
backend и прав больше не маскируются общим сообщением об отсутствии интернета.

Перед промышленной выкладкой обязательны проверки на целевой Windows-кассе:

- 100 последовательных сканов при отключённой сети и при HTTP-запросах без ответа.
- Перезапуск/принудительное завершение приложения после локального сохранения;
  затем синхронизация без потери позиций и дублей.
- Обрыв связи до/после принятия фискального запроса; неизвестный результат не позволяет повторную оплату.
- Одновременное изменение чека другим клиентом, изменение цен, истечение доступа,
  заполненный диск, недоступный ключ ОС и обновление большого каталога во время сканирования.

Целевой показатель для пилота: p95 «скан → сохранённая позиция на экране» менее 100 мс.
Это критерий приёмки, не измеренный SLA. Время банка/ККМ не входит в него.
Автоматические тесты не заменяют отключение питания и испытания настоящей ККМ.

Изолированный замер локального поиска на 100 000 синтетических товаров в дисковой
зашифрованной SQLite:
`POS_BENCHMARK=1 npm test -- src/main/pos/pos-search.benchmark.test.ts`.
Замер 2026-09-08 на машине разработки с новой порционной записью: 100 000 товаров
записаны за 8,18 с (без HTTP и сетевых пауз); p95 штрихкод 0,28 мс, текст 0,88 мс,
общее слово 1,55 мс. Проверка чтения и отдельной записи между страницами: p95 0,25 мс.
Это локальный тест, без IPC/React/сканера, не SLA Windows-кассы или DigitalOcean.
Точные коды выводятся первыми; текстовые совпадения — в стабильном порядке локального
индекса с пагинацией. Просмотр каталога без поискового слова остаётся алфавитным.
